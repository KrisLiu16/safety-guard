# 第一轮端到端计划：Luna 造数，M5 本地 RL、评测与推理优化

日期：2026-09-22。目标是完成一次有明确边界的实验闭环，取得真实的能力与速度对比，再决定第二轮。本文保留首轮执行规格；本轮已经完成，结果与未达预期项见 [ROUND1_REPORT.md](ROUND1_REPORT.md)，逐项验收见 `completion_audit.json`。下文阶段表为执行前快照。

本计划优先于旧计划中的“先等 L20 集群权限”“首轮同时研究全部新架构”等安排。详细机器参数和初始超参数保存在 [config.json](config.json)，实现入口和运行说明见 [README.md](README.md)。下文“待实施”表格保留为原计划快照，当前进度以运行产物为准。

**1. 固定首轮边界**

| 项目 | 本轮决定 |
|---|---|
| 本地硬件 | 已查实 Apple M5、32 GB 统一内存、macOS 26.7；工作磁盘可用约 812 GiB |
| 模型 | Qwen3Guard-Stream-0.6B，固定 revision `419364a715de9840d47b1457982f64ff37f90ed4` |
| 训练后端 | PyTorch + Transformers 的自定义风险分类实现，设备 `mps` |
| RL 方法 | 有限动作 policy gradient + 原版参考分布 KL；LoRA 和角色风险头更新，不生成 CoT |
| 数据生产 | Aster Luna，一词一个 Task，50 词 × 每词 100 条，目标 5,000 条 |
| 生成并发 | 用户已授权 50；每词重复 1，最多尝试 1，内部按 10 条/批顺序生成 |
| 公共 benchmark | Qwen3GuardTest，使用官方标签映射、位置定义和 strict/loose 指标 |
| 核心交付 | 原版基线、一个 RL checkpoint、完整/流式推理、前后能力对比、同质量速度对比 |
| 本轮停止点 | 报告一轮结果，不自动扩展词库、不无限调参、不自动启动第二轮 |

M5 的 32 GB 内存从模型规模看适合尝试 0.6B LoRA 和小 batch，但“能装下”不等于所有自定义算子、精度和反向传播均已验证。先做完整 forward/backward smoke test，不能仅依据芯片名称承诺吞吐或训练时长。

官方 PyTorch/Apple 支持通过 MPS 在 Apple silicon 上做 GPU 计算。[Apple MPS 文档](https://developer.apple.com/metal/pytorch/) 第一轮保留原生 Guard 分类结构以降低转换风险；MLX 的数组、自动求导、编译和缓存能力可用于后续后端实验，但不能直接将 `mlx_lm.lora` 的语言模型训练入口当成本模型的分类 RL trainer。[MLX 文档](https://ml-explore.github.io/mlx/build/html/index.html)

**3. 环境准备与本地可行性验证**

在项目下建立独立虚拟环境，优先选择依赖兼容的 Python 3.12/3.13，安装 PyTorch、Transformers、PEFT、Safetensors、Datasets 等必要包，固定实测可用的版本。当前系统 Python 未安装 torch、transformers、mlx，因此不复用系统环境假装已经可跑。

下载模型固定版本的权重、tokenizer 和自定义源码，检查源码后在本地加载。模型是 `Qwen3ForGuardModel`，必须保留输入/输出两套风险头及原类别映射，不能用普通 `AutoModelForCausalLM.generate()` 替代。

smoke test 的顺序：

1. 检查 `torch.backends.mps.is_available()` 和设备实际分配；先 FP32 处理 16 条短样本，记录 CPU 与 MPS 输出差异。
2. 将 `forward` 用于分类，检查 user/assistant 角色切换、padding、真实末 token 位置和官方 chat template。
3. 对 LoRA 参数和风险头做一次真实反向传播、优化器更新，确认 loss/梯度有限且参数确有变化。
4. 测试 BF16 forward/backward；支持且稳定才用于主训练，必要时回到 FP32 并降低 batch/长度。FP16 若采用必须单独检查梯度数值稳定性，不默认与 BF16 等价。
5. 首轮诊断禁止静默 CPU fallback；如果存在不支持算子，记录并改为等价受支持实现，再做一致性核验。不可将 CPU 跑完称为 M5 GPU 训练完成。

本轮训练上下文从 1,024 token 起步，microbatch=1；数据超长时单独隔离/缩短生成目标，不直接截断答案或改变监督位置。评测则在模型配置允许的总长 8,192 token 内尽可能保留原文。角色模板和本轮新增 token 都计入上限。

**4. Luna 数据生产：50 个词，每词 100 条，并发 50**

沿用已发布的 50 个固定词条 Task，新建独立 Run，使用已准备的 v2 生成模板和 `pilot/profiles/100-per-word/` 配置。已完成的 `aster-dev-253` 保持原样，不修改它的并发或产物。

- 每词 10 批，每批 10 条；同一词内部顺序请求，最多 50 个词并行，因此生成请求同时在途上限为 50。
- 目标 5,000 条例句、500 次生成请求；每批好坏各半，包含用户提问、安全回答、危险提问后的安全拒答、危险回答。
- 保留原始请求、响应、词库版本、模板版本、模型标识、token usage、每批时长、失败原因。只导出平台产物，不下载 API key。
- 保留最多尝试 1 次的约定，不因提取后不足 5,000 条就偷偷补采样。429/失败单独记录；如需补跑，按实际缺口另行安排。
- 依托前次试跑平均体量粗估约 146 万 token；新版提示和长度变化会改变实际用量。并发提高不代表总 token 或费用下降。没有核验单价，不提供金额承诺。

v2 提示针对首轮问题改进：禁止把真实人名前面加“虚构人物”以假装匿名；安全输入不得暗含欺诈/规避请求；风险证据必须在可判定前缀内。政治公共事务的正常提及、研究、引用、一般批评与具体有害行为分开标注。词库命中只控制题材，不自动定义违规。

生成规模检查可直接读取 `settings.json`。Aster 提交前执行 `flows check` 与 `runs plan`；本地并发配置不会自动修改旧 Run 或自动启动调用。

**5. 数据清洗、奖励校验与防泄漏**

现有 500 条 pilot 已产出 459 条结构合格记录，初筛 RL 候选 352 条（safe 228 / unsafe 124），另 107 条待复核。它适合调通代码和定位模板问题，不作为新模型最终测试集；候选不等于人工金标。

新生产数据通过现有提取脚本下载与校验，再增加以下步骤：

1. 原文哈希和近似重复过滤；同词不同批次不重复计算为新增独立语义能力。
2. 检查输入/目标角色、标签、风险类型、证据与前缀位置；数据加载时 observation 与 reward_spec 分离。
3. 合并别名/同义词族，例如政府/当局等同源表达；一词仍是一 Task，但多个 Task 可属于同一个 split_group。
4. 按词族和来源组预先冻结约 60% train、10% dev、10% calibration、20% test。由于词族大小不同、清洗损失不同，具体数量可能偏离 3,000/500/500/1,000；输出实际计数，不拆别名以凑数量。
5. 批次场景与生成模板跨组去重。正式数据与旧 pilot 若有相同词族/模板，只允许出现在同一划分或将旧 pilot 排除。
6. 对正常政治讨论、安全拒答、unsafe 证据与虚构上下文分别抽检；争议记录隔离。不得因为原模型判错就自动认定模型错，更不能直接按原模型输出修改测试标签。

最低数据检查：清洗后目标 ≥3,000 条，train 两个标签都要覆盖且所有目标角色均有样本；没有达到时仍可用合格数据跑小轮，但报告为较小数据试验，不自动扩充。按角色与标签采样平衡，不通过删光困难样本提高成功率。

针对本轮能力结论，冻结中文 test 的标签尽量来自独立复核。只能完成有限抽检时，单列“对 Luna 合成标签的一致性”，不把它称为真实世界准确率。未来让同一个 Luna 换 prompt 复核，也仍然是同源模型判断，并非独立金标。

**6. 训练前基线：先量出原版能力与速度**

保留两个推理实现：原始发布包装器，以及修复为只输入新增 token、真正复用 KV 的实现。先在同一权重上核验相同 token 前缀下的 logits/概率与最终判断，才能用修正路径做主评测。

能力基线：

- 本地冻结中文 dev/test：输入/回答分别报告 precision、recall、F1、正常误拦、复核比例；测试预测可先保存，但不能拿最终 test 选训练参数。
- 官方 Qwen3GuardTest：保留 thinking、thinking_loc、response_loc 的定义与包含关系；迁移其计算到 MPS 时不改变标签映射、模板和 metric 公式。
- 位置分片全是风险例，不能据其报告正常误拦率；中文小测试负责补充这一观察。[官方数据卡](https://huggingface.co/datasets/Qwen/Qwen3GuardTest)

本轮优先跑所有在原生上下文范围内、能在预算内完成的官方样本。先做固定 smoke 子集检查运行成本：例如 thinking 100、response_loc 100、thinking_loc 50，按 ID 固定并与训练隔离。若单个 checkpoint 的全量评测预计超过 1 小时，就使用预先冻结的本地评测子集完成首轮，明确写“官方数据子集结果”，不得宣称全量排行榜成绩。超长样本单列为 unsupported/overlength，报告覆盖率，不静默截断。

**7. M5 上的一轮 RL 配置**

本轮“一轮”指从基线、数据、一次有限训练、验收到优化报告的完整实验；不是无限多次换参数追分。

| 参数 | 初始配置 |
|---|---|
| 更新参数 | 最后 8 层 q_proj/v_proj 的 LoRA，rank 8、alpha 16；输入/输出风险头 |
| 保留部分 | 原始主干基础权重冻结；风险类别头不作无标签更新 |
| 微批次 / 梯度累积 | 1 / 16，累计约 16 个有效例后更新 |
| 序列长度 | 1,024 token；超长隔离，不静默截断 |
| 时长与步数 | 1 次数据遍历或 300 个 optimizer step，先到者停止；训练活跃时间最多 2 小时 |
| 学习率 | adapter 3e-6，风险头 1e-5，gradient clip 1.0 |
| 参考约束 | 固定原版分布 KL，beta 初始 0.02；不是经验最优值 |
| 策略采样 | 每个实例从 3 类风险分布采样 4 个分类动作，不重复 4 次主干前向 |
| 保存与开发评测 | 每 50 step 和结束时保存；checkpoint 只按 dev 选择 |
| 第一轮 seed | 20260922；先跑一个 seed，重复稳定性留给第二轮 |

采用有限动作的 policy gradient：分类动作按独立 verifier/已校验合成标签获得奖励，错判扣分，争议动作作为有成本的不确定处理。考虑 safe/unsafe 数据缺少真正 controversial 金标，不能把输出 controversial 永远当成无代价正确答案；也不能通过训练把原模型所有争议能力直接抹掉，原版 KL 和官方回归共同约束。

少量标注、可枚举动作和目标风险明确时，可以算精确期望奖励作为方差对照；如果引入交叉熵等辅助项须单独记录，保持主实验为用户选择的 RL。训练奖励改善与 dev 误拦/漏检一起看，奖励上升不是最终成功证据。

为了减少 M5 内存和重复计算，可在固定训练实例及前缀上预先计算原版参考概率，保存输入 token hash、角色和位置，再只保留一份可训练模型驻留。训练时权重变化，不能复用旧训练步的 KV 或旧隐藏表示来假装更新了主干。`use_cache=False` 用于有反向的训练路径，推理缓存是另一条路径。

流式能力本轮采取轻量方式：从具有可靠前缀标注的训练例采样少量前缀进行 RL，同时评测风险定位；放行/暂存/阻断控制器先用固定阈值和 buffer。学习完整序列控制策略 RL-B 不作为第一轮完成的前提，留待静态收益与前缀质量验证后进行。

概率校准使用独立 calibration 集，测试集不参与选阈值；小集合不足以支持极低误拦率的统计保证。保存预校准与校准后分数，不能通过不断增加 review 让安全率虚高。

**8. M5 资源和停损条件**

- 目标训练工作集约 20 GiB 内，持续超过 24 GiB、系统内存压力明显升高或 swap 持续增长时暂停并减小长度/批次，给桌面和系统留空间。这是运行阈值建议，不是已验证占用。
- 首先测 20 step；记录每步耗时、有效 tokens/s、峰值内存，再给出该配置的一轮预计时间。不得先承诺“半小时训练完”。
- 遇到 NaN/Inf、梯度长期为零、风险头参数未更新、标签泄漏或缓存不一致，停止长跑并修正确性。
- 若 20 step 估计超过本轮 2 小时训练预算，先缩短为 100 step 或 1,000 条数据的小轮，记录实际训练量；不无限占用用户电脑。
- 充电、散热、是否有其他高负载应用必须记录；性能测试和训练不并行争抢 M5。
- 不通过关闭系统内存保护、允许无限 swap 或静默 CPU fallback 来强行跑完。

**9. 训练后评测与成功判定**

用与基线相同的数据版本、分词和模板，比较 Original-CorrectCache 与 RL-M5。先看分类质量，再看流式读出；两种模型都校准到相同误拦或相同复核预算进行公平比较。

必须有一张对比表：输入/回答 F1、Recall@相同 FPR、正常误拦、controversial/review 比例、官方 strict/loose 指标、首个风险检测位置与漏检、分组样本数和置信区间。

第一轮合格不以“所有分数必须提升”定义，而以结果可重复、无数据泄漏、比较公平且明确是否获益为准。能力目标是中文目标集在相同误拦约束下减少漏检，并尽量让官方指标下降不超过 1 个百分点；达不到就输出失败分析，不用测试集改奖励后重新宣称本轮成功。

没有达到显著改进时，仍完成本轮报告和基线推理优化，下一轮优先检查奖励和语料分布。一个 seed 和同源合成 test 的小幅提升，不作为已解决通用安全审查的证据。

**10. 本轮必做推理优化：针对 Apple Silicon**

Mac 上不采用 CUDA Graph 或 CUDA FlashAttention kernel。首轮优化采用真正增量缓存、MPS 受支持 attention、长度分桶、适度 batch、减少 Python/拷贝开销，并评估 adapter 合并；任何 compile 路径先核实本机 backend 支持，不假定 CUDA 的经验可直接迁移。

| 优化 | 目的 | 本轮要求 |
|---|---|---|
| 增量 KV Cache | 历史只 prefill 一次 | 必做；与同前缀全量结果对齐 |
| 角色与消息前缀复用 | 避免审完 user 后回答到来又重复编码历史 | 必做；结束标记、重分词与多轮追加处理正确 |
| 审查 chunk 1/8/16/32 | 减少调度开销，观察延迟取舍 | 必做；把等待凑块时间计入用户延迟 |
| 长度分桶 / batch 1/2/4 | 提升处理多条对话时的设备利用率 | 必做；吞吐与 P95 一起报告 |
| LoRA 合并 | 减少 adapter 额外矩阵计算 | 验证等价后比较；保存原 adapter，禁止覆盖原始权重 |
| MLX 原型 | 比较 Apple Silicon 原生执行性能 | 本轮可选；只迁移一份已冻结 checkpoint，保留原风险头并做输出对齐，不能用聊天权重代替 |
| 低比特量化 | 降低内存带宽和缓存容量 | 可选；必须有对应后端支持和量化后能力回归 |

MPS 计时需同步设备，MLX 若测试则显式求值并同步，不能只测 Python 提交任务的时间。分别报告冷启动、热推理、prefill、每块延迟、总等待、吞吐和峰值统一内存；每种配置先热身，再重复测量。

负载网格：256/1k/4k/8k 的总上下文，末档预留续流空间；并发 1/2/4，batch 1/2/4，chunk 1/8/16/32。先稀疏选点找到可行范围，再细测，不把整个笛卡尔积全部重复长跑。模型前向延迟与端到端审查延迟分开。

首轮至少交付“原发布实现 / 同权重正确缓存 / RL 权重正确缓存 / 一个进一步优化版本”的结果。优化目标为某个有代表性负载 P95 降低约 20% 或同 SLO 吞吐提高约 30%，这是实验目标，不是承诺；没有提升也必须报告真实结果。

MoE、DSA、MLA 的结构研究移到第二轮入口：只有本轮 profiling 表明对应计算/访存值得优化，且模型能力已建立可信基线时才投入。两张 L20 也保留作为后续加速资源，本轮不依赖集群权限。
