# 第五轮复盘：前缀误报的来源与门槛噪声

2026-09-24。只用已取回的预测文件在 CPU 上分析，没有调用模型。复现方法：`.venv/bin/python round5/diagnose_prefix_leak.py`，结果写到 [diagnosis/prefix_leak_diagnosis.json](diagnosis/prefix_leak_diagnosis.json)。官方集只做描述性观察，没有用来选权重或调阈值。

## 1. 流式误报主要来自提问风险泄漏到回答判定

官方 thinking 分片使用“连续两次 Unsafe”规则：

| 标签 | 条数 | 触发数 | 在前 2 个 token 内触发 |
|---|---:|---:|---:|
| Safe | 490 | 440（89.8%） | 341 |
| Unsafe | 569 | 560 | 455 |

大部分决定在思考内容刚开始、模型几乎只看到用户提问时就已经做出。流式召回 98% 主要是在判断提问本身，而不是在读回答。

canonical32 开发集（初始权重）在回答第 1 个字符处的 p_unsafe 如下：en/assistant 中，safe 样本有 24.5% 超过 0.5，unsafe 样本有 60% 超过 0.5，两者中位数分别是 0.04 和 0.76。按 0.5 阈值，流式 FPR 为 zh/user 31%、zh/assistant 29.5%、en/assistant 63%。开发集上报出的 6.5% 靠的是 0.993–0.996 的校准阈值。这也导致召回上不去：en/assistant 的流式召回只有 54.5%。

这个捷径是训练数据教出来的。在 Nemotron zh 的 assistant 训练记录里：

| 提问 → 回答 | 条数 |
|---|---:|
| unsafe → unsafe | 2,500 |
| unsafe → safe | 1,286 |
| safe → safe | 1,214 |
| safe → unsafe | **0** |

也就是说，单看提问就能大体猜出回答标签。开发集和校准集有同样的偏差，所以当前开发集发现不了这个问题。BeaverTails 的 7,766 个提问中，只有 2,482 个同时带有 safe 和 unsafe 回答。

第五轮的前缀标签规则让 unsafe 回答的中途位置全部 mask，safe 回答的前缀只给 0.05 的有效权重（0.1 × 0.5）。因此在“回答刚开始”这个位置，模型几乎没有受到任何反向约束。

## 2. 第五轮的门槛结论主要是阈值落点噪声

同一开发集，按家族（family）做 1,000 次成对自助采样，下表是相对初始权重的差值和 95% 置信区间：

| 检查点 | 整段 AUC | 流式 AUC | 同 5% FPR 下的流式召回 |
|---|---|---|---|
| SFT epoch1 | −0.4 [−1.5, +0.5] | +0.3 [−1.0, +1.6] | +2.7 [−3.7, +11.5] |
| SFT epoch2 | −1.4 [−2.3, −0.5] | +1.2 [−0.2, +2.5] | +2.7 [−4.5, +9.6] |
| RL 256 | −0.1 [−0.3, +0.0] | −0.2 [−0.4, −0.0] | −0.7 [−2.7, +3.5] |

门槛报告里“SFT 整段召回下降 5.7 个百分点”，主要是因为校准阈值在开发集上落到了不同的误报率（初始 6.8%，epoch2 5.2%）。放在同一误报率下比较，召回差异都落在噪声范围内。每层 200 个 safe、校准 150 个 safe 的规模，分辨不出 ±5 个百分点的变化。三层同时满足 FPR ≤ 5% 这个门槛，对一个完全不变的模型也大约只有两成的通过概率。

## 3. 对第六轮的含义

1. 需要 assistant 侧数据，并且要按同一提问配对 safe 和 unsafe 回答，让提问本身不再携带标签信息。还要标出 unsafe 起点：起点之前的前缀给 hard safe，之后给 unsafe。
2. 开发集和校准集要重新构造：加入“危险提问 + 安全回答（拒答、思考式分析、中性讨论）”，并增大样本量。选模改为用校准集阈值，同时报告不依赖阈值的指标（AUC、同 FPR 下的召回）和置信区间。
3. 在修正数据之前，不值得再做同设置的 SFT 或 RL。第五轮 RL 在 256 步内几乎没有改变模型。
