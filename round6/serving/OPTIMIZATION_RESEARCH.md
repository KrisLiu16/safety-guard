# 推理引擎 v6 优化空间调研（2026-09-25）

调研范围：一张 L20 上的流式审核引擎 v6（`bucketed_engine.py` + `gdn_slot_kernel.py` + `ring_attention_kernel.py`），
以及 FLA、vLLM、SGLang、FlashInfer 等外部实现的现状。英文原稿和全部链接见 `paper/notes/06_serving_optimization.md`（本地）。

## 结论

- **还有不损失精度的空间，而且不小。** 现在每个 tick 只用到显存带宽上限的约 39%，主要浪费在大量小 kernel
  的启动开销和小矩阵乘法没占满 SM 上，不是算力或带宽不够。
- 四项“结果逐位相同或只差浮点舍入”的改动（下表 1–4）合起来，**估计**容量从 208 个会话提到 **280–320 个**
  （P95 ≤ 20 ms 不变）。这是模型推算，**还没实测**。
- 有损的（8 位权重量化）大约再加 20–30 个会话，要单独过精度门槛；8 位递归状态不做（bf16 状态已经没过漂移门槛）。
- 不用换 SGLang / vLLM：它们解决的是生成，我们的负载（每次追加 1–4 个 token、不生成、逐 token 出分、要能回退）
  它们目前都不擅长，结论见第 6 节。

## 1. 现状（v6，`results_v6/report.json`）

| 会话数 | tokens/s | P50 | P95 | P99 |
|---|---|---|---|---|
| 208 | 8,817 | 13.6 ms | **18.0 ms** | 18.6 ms |
| 224 | 9,469 | 15.5 ms | 20.5 ms | 21.0 ms |
| 256 | 10,820 | 24.3 ms | 47.4 ms | 239.8 ms |

- 208 个会话时，每个 tick 8.75 ms（每秒 114 个 tick），平均每个 tick 带 77 个会话、每个会话 1 个 token。
- 用 208 和 224 两点拟合：**tick 时间 ≈ 3.57 ms 固定开销 + 每行 67 µs**，P95 约为 tick 时间的 2.06 倍。
  固定开销省 1 ms 或每行省 10 µs，大约多带 35–40 个会话。

## 2. 每个 tick 的时间花在哪（208 个会话）

| 部分 | ms / tick | 依据 | 带宽下限（ms） |
|---|---:|---|---:|
| GDN 递归（77 个会话的 fp16 状态读 + 写） | ~2.0 | 实测（192 行时每会话 26.4 µs，按比例换算） | 1.68 |
| 权重矩阵乘法（186 次 launch，995 MB bf16） | ~2.3–2.5 | 实测（128 行 2.66 ms，192 行 3.0 ms）；96 行这个档没单独测过 | 1.15 |
| 滑窗注意力（ring） | ~0.85 | 实测（约 65% 带宽） | 0.56 |
| 短卷积链（index、cat、conv1d、silu、gather、index_put、3 次 contiguous） | ~0.9 | 实测（v5 profile 换算）；流量约为最小值的 12 倍 | ~0.1 |
| 其他小 kernel（RMSNorm、rope、类型转换、拷贝、加法，约 1,000 次 launch） | ~1.6–2.0 | **估计**（kernel 数来自代码，profile 确认） | ~0.2 |
| 两个头（autocast 每次把 fp32 头权重转 bf16；类别头算了又丢） | ~0.1 | 估计 | — |
| 图外：clone、154 次 `torch.cat`、拷回 CPU | ~0.2–0.3 | 估计 | ~0 |
| 启动前的 CPU 串行工作（扫 208 个会话、逐行 Python 填数组、4 次会同步的 `copy_`） | ~0.5–0.7 | **估计，没打点** | ~0.05 |
| **合计** | **~8.5–9.4**（实测 8.75） | | **~3.4** |

- **带宽上限**：每个 tick 必须读写的数据约 2.94 GB（权重 1.0 + GDN 状态 1.45 + ring 0.49），864 GB/s 下要 3.4 ms。
  实际 8.75 ms，即约 **39%**。
- 分类看：约 45% 是启动/延迟瓶颈（每张 CUDA graph 约 1,350 个节点，小矩阵乘法 SM 占不满），约 40% 是带宽瓶颈
  （GDN 和 ring 两个自写 kernel，已到带宽的 65–89%），7–10% 是 CPU 串行。
- 所以整体还没到带宽瓶颈；GDN 单项已经接近它自己的上限，再抠它收益不大。

## 3. 不损失精度的优化（按“收益 / 工作量”排序）

各项单独估计，互有重叠（2、3、4 都在减 launch），**不能直接相加**。

| # | 改动 | 估计收益（会话数） | 工作量 | 风险 | 结果一致性 |
|---|---|---|---|---|---|
| 1 | **CPU 路径和图内清理** | +25…+50 | 0.5–1 天 | 很低 | **逐位相同** |
| 2 | **短卷积 + SiLU + 切分融合进 GDN slot kernel** | +30…+54 | 2–3 天 | 低 | 浮点舍入级 |
| 3 | **融合逐元素算子链**（约 1,350 → 250 个节点） | +44…+66 | 2–5 天 | 中 | 浮点舍入级 |
| 4 | **矩阵乘法拼接 + 小 M 的 split-K** | +22…+37 | 2–3 天 | 低 | 浮点舍入级 |
| 5 | 变长 token 打包（去掉 Lb=2 的悬崖） | +8…+16 | 3–4 天 | 低 | 浮点舍入级 |
| 6 | 延迟写状态（ReplaySSM 思路） | +26…+43 | 1–2 周 | 中（数值） | 需实测漂移 |
| 7 | ring 注意力：split-KV、流水线、融合写入和 gate | +10…+15 | 1–2 天 | 低 | 浮点舍入级 |

**合起来**：1–4 做完，固定开销约 2.2 ms、每行约 51 µs，模型给出约 355 个会话；但每个 tick 超过约 140 行后矩阵乘法
变成算力瓶颈（L20 规格表算力 / 带宽 ≈ 138 FLOP/byte，规格数未核实），**按 280–320 个会话计划**。

### 每项具体做什么

1. **CPU 路径和图内清理（逐位相同）**
   - 每个 bucket 预分配 pinned 缓冲区，用向量化 numpy 填，代替 `bucketed_engine.py:199-201` 的逐行循环；H2D 用 `non_blocking`。
   - 结果一次性拷回 pinned 内存 + event，代替 154 次 `torch.cat` 再 `.cpu()`。
   - 把输入收集移出 tick 线程（基准里每个 tick 都用 Python 重扫 208 个会话）。
   - 图内：头权重预先转 bf16（autocast 本来每次都转，结果逐位不变）；去掉算了又丢的类别头；删掉 inplace 模式下已经没用的
     `allowed` / `key_pos` 掩码（`bucketed_engine.py:79-83`）；删掉 `gdn_slot_kernel.py:79` 的 `zeros_like` 清零。
2. **卷积融合进 GDN kernel**
   - 每个 program 已经负责一个 head 的 q/k 和一段 V，直接从 `conv[slot]` 读 3 个历史值、卷积、SiLU，按现在相同的两处舍入到 bf16，再写回历史。
   - 每层少约 12 次 launch，每个会话每 tick 少约 8 MB 流量。
   - 对照：SGLang 在 H20 上做同类融合基本持平（PR #35758），但它原本就是一个 in-place kernel；我们现在是 9 个 kernel 的链，收益更大。
   - 顺带把 gated RMSNorm 融进 epilogue（BV=128）。v5 的扫参显示大 batch 时 (128, 8) 和 (32, 2) 一样快。
3. **融合逐元素算子**：残差加 + RMSNorm（48 处）、SiLU·mul、每个注意力层一个 q/k-norm + 部分 rope + 转换 kernel、注意力 gate 融进 ring kernel。
   两条路：`torch.compile` 包每层的胶水代码（Triton kernel 注册成 custom op），或手写 Triton。求和顺序会变，所以只能做到浮点舍入一致。
4. **矩阵乘法拼接 + split-K**
   - 拼接 qkv+z+b+a（N=8224）、gate+up（N=7168）、注意力 q+k+v（N=5120）：186 次 launch 降到 96 次，去掉 36 个只跑 1 个 CTA 的 N=16 小乘法。
   - N=1024 的三类乘法（down、out、o_proj：48 次 launch，占权重字节 28%）用 128×64 的 tile 只能开 16–32 个 CTA，而 L20 有 92 个 SM，
     这可能是矩阵乘法只到约 43% 带宽的原因。办法：Triton split-K，或 cuBLASLt 加大 workspace（它会不会选 split-K 未核实）。
   - TunableOp 没用：CUDA 版只跑默认的 cuBLAS 方案。
5. **变长打包**：224 → 240 个会话时 P95 从 20.5 跳到 51 ms。原因是有些会话一个 tick 攒了 2 个 token，**整个 tick 就按 Lb=2 补齐**，
   矩阵乘法行数翻倍、tick 变长、更多会话攒 2 个 token，恶性循环。改成扁平布局（总 token 数 + offset，两个 kernel 本来就接受 `lens`）。
   稳态 ≤224 时没收益，主要管边缘和突发流量。
6. **延迟写状态**：递归可以展开成“读一次初始状态 + 若干个秩 1 更新”，每 r 个 token 才写一次状态。r=8 时每会话每 token 流量从
   18.9 MB 降到约 11 MB。数学上精确，而且状态舍入到 fp16 的次数变少，漂移理论上会变小，但要实测。公开实现只支持 SM90+，要自己写 Triton 版。
7. **ring 注意力**：现在每个会话 2 个 CTA、`num_stages=1`、`block_n=32`。把 512 的窗口拆给 2–4 个 CTA 再合并，开 2–3 级流水线；
   Lb=1 时先把新 K/V 写进 `pos % W` 那一列（正好是被挤掉的那个 key），注意力就只读 ring，还能去掉第二个循环、两次 index_put 和几次 contiguous。

## 4. 有损优化（要单独过精度门槛）

| 改动 | 估计收益 | 精度风险 |
|---|---|---|
| **权重 8 位（W8A16，int8 或 FP8 E4M3，按通道）** | 矩阵乘法下限 1.15 → 0.58 ms；做完第 4 项后约 **+20…+30** 个会话 | 低到中；按通道 int8 通常比 E4M3 更接近无损 |
| 权重和激活都 8 位（W8A8 FP8） | 带宽同上，另加 2 倍张量算力；只有超过约 140 行/tick 才有用 | 中（激活量化） |
| 8 位 GDN 状态 | 约 +48 | **高**：bf16 状态已经没过漂移门槛（最大 cut 差 0.21–0.30），不做 |
| FP8 KV ring | 约 +12 | 中 |

- W8A16 的 kernel：vLLM 的 FP8 Marlin 支持 SM90 以下，但只在 A10/A100/H100 上测过；或者自己写 Triton 反量化 split-K。
- W8A8：torch 2.7.1 的 `_scaled_mm` 支持 SM89（按行缩放走 CUTLASS sm89 kernel，只出 bf16）。有报告说 torch 2.11 上 SM89 按行缩放在 CUDA graph 回放时会卡住，要显式测。
- **精度门槛**：量化引擎对 bf16 整段前向的漂移（`bench_v6_l20.py` 的 decision_drift 集）；阈值是在 bf16 上标定的，要重跑 dev 的误报和召回；
  触发决策的差异数不能多于 v6。注意 v6 自己在 400/800 条集合上最大 cut 差已经是 0.26–0.28，所以“最大差 ≤ 0.15”这条门槛对 v6 本身都不成立，
  改用 p99.9、超过 0.1 的计数和决策差异，以 v6 为基线。

## 5. 评估过、不推荐的

- **攒批 / 按到达时间微批**：引擎已经把每个 tick 所有待处理 token 都塞进去了。按我们的到达模型（每会话 30–60 token/s），
  故意等第二个 token 要多等 17–33 ms，超过 SLO。**但真实流量如果是一次来 2 个 token 的突发，容量能涨约 40%**（同一会话多一个 token
  只多约 22 µs，新开一行要 55–67 µs）。所以**测一下上游 SSE 实际每次推多少 token，是性价比最高的实验**。
- **分层流水线（wavefront）**：P95 反而变差（约 2.95T 对 1.95T）。
- **L2 常驻**：权重 1 GB 远大于 L2，状态在约 22 ms 内不复用，收益约 0。
- **MPS / 多实例**：每个实例都要重读权重、付自己的固定开销，P95 变差。多进程只用在 CPU 侧。
- **Megakernel**：1–4 做完后只剩约 250 次 launch（0.3–0.4 ms），几周工作量换 +10…+20 个会话。现有实现（MPK、ThunderKittens）面向 A100/Hopper/Blackwell。
- **CUDA graph 条件节点**：torch 2.12 才有；设备端 graph launch torch 没暴露。
- **分词和回退**（生产风险，不是基准里的成本）：测试台每次更新都重新编码整段对话、做一遍最长公共前缀扫描，还深拷贝缓存（`guard_demo/server.py`）。
  每秒约 9,400 次更新、每段几千 token 时，要几十个 CPU 核。上生产前要改成从 HOLD_BACK 尾部之前的边界增量编码，并离线对照整段编码验证；
  每约 64 个 token 给 slot 存一个快照（每次约 38 µs 的 GPU 拷贝，<1% GPU 时间）。

## 6. 外部现状（L20 是 SM89，能用的只有 Triton）

- **FLA**：最新仍是 v0.5.2（2026-07-27）。上游 `fused_recurrent` 没有 in-place 的状态索引，固定 BV=8 / 1 warp，比我们的 kernel 慢。之后的提交是 XPU/昇腾调优。
- **vLLM 的 decode kernel**：Triton、在 kernel 内做 gating、in-place 状态、BV=32 / 1 warp——**基本就是我们 v4 的设计**；它的 `causal_conv1d_update` 仍是单独的 kernel。
- **SGLang**：BV 从 8 改到 32 带来约 10% 端到端提升；sigmoid(β) 保持 fp32 修复了状态漂移（我们的 kernel 本来就这么做）。
- **只支持 Hopper / Blackwell 的**：FlashInfer GDN decode、FlashQLA、FlashKDA、cuLA 都要求 SM90+，L20 用不了。
- **没找到**：Liger、MiniMax、TileLang 的 SM89 decode kernel。

**能不能换成 SGLang？**（v0.5.20 源码和 issue，详见 `paper/notes/05_sglang_evaluation.md`）
- 能跑我们的主干（Qwen3.5-0.8B 纯文本类在 v0.5.17 加入，正好在 0.8B 上验证过），有流式 session。
- 但：GDN 的追加永远走 chunk kernel，没有短追加的快路径（估计 GDN 部分是我们的约 2 倍）；流式 session 不能回退或分叉；
  逐 token 输出只能借 hidden states 通道；混合模型上的滑窗没验证过；每秒约 9K 个请求的 CPU 开销没人测过；v0.5.20 要 CUDA 13。
- vLLM：混合模型的前缀缓存按约 528 token 对齐，回退后一个小追加可能要重算近一个块。
- **结论**：生产不换。上游生成模型可以用它们；审核模型保留 v6。要想确证，可以花 2 小时在一张 L20 上跑一个 SGLang 吞吐对照（方案在英文原稿里）。

## 7. 验证计划（约半天，一张 L20，都基于 `bench_v6_l20.py`）

1. **打点基线（约 45 分钟）**：v6 在 208 会话下跑 `nsys --cuda-graph-trace=node`，拿每张图的节点数、kernel 时长和空隙；
   `simulate`/`step` 里加 CPU 时间戳；对每种权重形状在 M ∈ {80, 96, 128, 160, 224} 下比较 cuBLAS 默认、cuBLASLt、Triton split-K。
   用实测替换第 2 节里的估计行。
2. **A = 第 1 项**：概率与 v6 **逐位相同**（最大差 0）；P95 在 208 会话 ≤ 17 ms，224 会话 ≤ 20 ms。
3. **B = A + 卷积融合**：kernel 单测输出差 ≤ 1 个 bf16 ulp、状态差 ≤ 1 个 fp16 ulp；对整段前向的漂移：每个集合、规则、阈值下的
   决策差异数 ≤ v6，p99.9 cut 差 ≤ v6 的 1.1 倍（思考 0.038、安全 0.069）；对 v6 的 p99.9 ≤ 0.01；P95 在 240 会话 ≤ 20 ms。
4. **C = B + 矩阵乘法拼接 / split-K**：同样的门槛，P95 在 256 会话 ≤ 20 ms。
5. **D = C + 融合逐元素**：同样的门槛，另加 graph 与 eager 差为 0；在 208–320 会话、每点 16 秒、2 个种子下测，目标 272 会话以上 P95 ≤ 20 ms。
6. **顺带**：把录下来的上游 SSE 分块大小回放进 `simulate`，看容量对突发有多敏感。

第 6 项（延迟写状态）和 W8A16 量化另开，按第 4 节的门槛单独验收。
