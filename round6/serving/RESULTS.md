# 第六轮速度线：连续批处理引擎

2026-09-24。所有测试都用第五轮固定权重（bb16a3a6…），在单张 L20 上完成，不训练。目标（用户已定）：单次分类 P95 ≤ 20 ms 的前提下，单卡 ITPS 最大化；只保留流式一条计算路径，不要求逐位一致。

## 三个版本

| 版本 | 文件 | 做法 | 结果目录 |
|---|---|---|---|
| v1 | [batched_engine.py](batched_engine.py) | 变长拼批，每层现造索引，FLA chunk 内核 | `results_v1/` |
| v2 | [bucketed_engine.py](bucketed_engine.py) | 按（会话数, token 数）分桶，右侧补齐且不改状态，每个桶捕获一个 CUDA Graph | `results_v2/` |
| v3 | [slot_engine.py](slot_engine.py) + [gdn_slot_kernel.py](gdn_slot_kernel.py) | 自写 GDN 内核：按槽位原地读写状态池，只算真实 token，门控、β、L2 归一在内核内完成；注意力按 KV 头分组手写，不复制 KV | `results_v3/` |

v2 到 v3 的改动依据是 profiler 结果（`profile_v1/`）：在 128 个会话 × 每人 1 个 token 的一步里，SDPA 退回 math 实现占 35 ms，状态的 gather/scatter 约占 20 ms，逐元素的门控计算约占 10 ms。

## 正确性（与整段一次前向对比，14 条官方 thinking 长序列，共 18,589 个位置）

| | 最大差值 | 99.9 分位 | 99 分位 | argmax 翻转 |
|---|---:|---:|---:|---:|
| v1 | 0.306 | 0.034 | 0.0044 | 4 |
| v2 | 0.115 | 0.015 | 0.0028 | 2 |
| **v3** | **0.039** | 0.017 | 0.0033 | 2 |

v2 和 v3 在使用 Graph 与不用 Graph 时输出完全一致。最大差值都出现在参考概率约 0.55 的位置，那里对数值扰动敏感；在 0.99 以上的校准阈值下不影响判决。

## 速度（v3）

固定负载（N 个会话，每个每步追加 c 个 token）：N=1、c=1 时每步 3.75 ms；128×1 为 18 ms；512×1 为 63 ms；峰值约 3.55 万 ITPS（64–128 个会话 × c=16）。每个会话每步开销约 0.115 ms。按带宽算的下限约为 0.044 ms：每步要读写 18.9 MiB 的 fp32 GDN 状态，L20 带宽 864 GB/s。

模拟真实到达节奏（每个会话每秒 30–60 个 token，统计每个 token 从到达到结果回到 CPU 的延迟）：

| 并发会话 | ITPS | P50 | P95 | P99 |
|---:|---:|---:|---:|---:|
| 32 | 1,280 | 8.1 ms | 10.6 ms | 11.2 ms |
| 64 | 2,625 | 9.8 ms | 12.9 ms | 13.4 ms |
| 128 | 5,334 | 23.7 ms | 31.4 ms | 32.2 ms |
| 192 | 8,080 | 61 ms | 81 ms | 83 ms |
| 256 | 10,817 | 68 ms | 91 ms | 237 ms |

结论：在 P95 ≤ 20 ms 的要求下，单卡目前能承载约 64–100 个真实速度的流式会话，约 2,600–4,500 ITPS。大段一次性输入的峰值可到约 3.5 万 ITPS。

## 下一步（按预计收益排序）

1. GDN 状态改为 BF16：流量减半，需要实测精度漂移。
2. 注意力的环形缓冲改为原地读取，不再 gather 复制。
3. 权重改 FP8，压缩每步约 3.7 ms 的固定开销。
4. 把 A0 放到同一个引擎上做对比测速。

## v4（T007，2026-09-24 实测，结果目录 `results_v4/`）

本轮只做“下一步”的第 1、2 项，第 1 项顺带扫 GDN 内核的分块参数：

| 改动 | 文件 | 依据 |
|---|---|---|
| GDN 状态池可选 fp32 / bf16 / fp16。内核本来就在 fp32 寄存器里算，一个 tick 内的多个 token 都在寄存器里累积，每个 tick 只取整一次 | [slot_engine_v4.py](slot_engine_v4.py)、[gdn_slot_kernel.py](gdn_slot_kernel.py) | 每个会话每步的实测开销约 0.115 ms，其中 fp32 状态读写约 37.8 MB，按带宽算约 0.044 ms。换成 16 位后这部分减半。fp16 比 bf16 多 3 位尾数，精度可能更好，两种都测 |
| 注意力按槽位原地读环形缓冲（Triton，融合掩码和在线 softmax），不再先 gather 复制 | [ring_attention_kernel.py](ring_attention_kernel.py) | v3 每个会话每层要 gather 约 1 MB 的 K/V，然后两次矩阵乘再读一遍 |
| GDN 内核的 V 方向分块宽度和 warp 数可调（v3 为 8 和 1） | 同上 | v3 的分块很小，可能没吃满带宽 |

[bench_v4_l20.py](bench_v4_l20.py) 在同一次运行里依次测：
1. 新注意力内核与 torch 参考实现在随机输入上的对比；
2. 六种组合（状态精度 × 环形缓冲读法）和 v3 相对整段前向的漂移，同时报告 p(unsafe) 和红线口径的截断分数 1 − p(safe)，并用漂移门槛筛选组合；
3. GDN 内核分块参数的扫描；
4. 通过门槛的组合与 v3 的固定负载吞吐，以及真实到达节奏下的延迟，报告 P95 ≤ 20 ms 时能承载的会话数。

第 3、4 项（FP8 权重、A0 同引擎对比）这一轮不做：
- FP8：权重每步只占约 1.7 ms 的读取，在 128 个会话时不是瓶颈。另外，L20 上 `torch._scaled_mm` 的逐行缩放是否可用还要先确认，只能按整张量缩放的话精度风险大。
- A0：要为 A0 另写一个同样的连续批处理引擎（全注意力、KV 缓存），工作量大，而且只是对比，不提速。

### v4 结果

- **容量翻倍**：fp16 状态 + 原地读注意力 + GDN 分块 (32, 2)，在 P95 ≤ 20 ms 时能承载 **192 个**真实速度的流式会话（约 8,100 ITPS，P95 18.5 ms），v3 是 96 个。
- **固定负载**：128×1 每步 18.1 → 11.1 ms；512×1 每步 62.8 → 35.2 ms。每个会话的状态从 25.8 MB 降到 16.4 MB。
- **各项的贡献**（按 P95 ≤ 20 ms 的会话数）：原地读 96 → 128；再换 fp16 状态 → 160；再换分块 → 192。
- **精度**：各组合漂移最大的位置都是同一个（序列 353 第 897 位，参考概率 0.55，恰在判决边界上，v3 的最大值也在这里）。除这个位置外，最大差都在 0.055 以内；p99.9 在 0.015–0.022 之间，和 v3（0.017）相当。bf16 状态只因为这一个位置超过门槛，而 fp16 精度更高、速度相同，所以不再考虑 bf16。
- **fp32 下原地读也会带来漂移**（最大值 0.039 → 0.143，但也是这个位置）。原因是 softmax 的归一化顺序：v3 先归一化再转 bf16，内核在线累积、最后才归一化，舍入不同。这类差异只在接近 0.5 的敏感位置被放大。

### 下一步（T007 v2）

逐位置的最大差只由一两个敏感位置决定，说明不了判决会不会变。[bench_v5_l20.py](bench_v5_l20.py) 改为：
- 在 400 条官方 thinking 序列上，用同一套随机切分，统计各个阈值和规则下流式判决与整段前向不一致的序列数；
- 对 fp16 按批大小选分块（(32, 2) 在 128 会话最快，512 会话时 (64, 4) 更快）；
- 剖析 192 会话的一步，看下一个瓶颈在哪里；
- 用按批大小选的分块复测容量。

## v5（T007 v2，2026-09-24，结果目录 `results_v5/`）

- **判决一致**：400 条官方 thinking 序列、374,953 个位置。阈值不超过 0.9 时，fp16 + 原地读的流式判决与整段前向完全一致，threshold 和 consecutive_2 两种规则都是如此。阈值在 0.95–0.99 时，只有 0–2 条序列不一致，v3 在 0.99 也有 1–2 条。逐位置的 p99.9 为 0.037，v3 为 0.036。
- **按批大小选分块没有收益**，固定用 (32, 2)。P95 ≤ 20 ms 时承载 **208 个**会话（v1 的模拟只测到 192）。
- **剖析（192 个会话，每步 1 个 token）**：会话数从 128 增加到 192，GDN 内核从 3.0 ms 涨到 6.5 ms。原因是 192 个会话会补齐到 256 的档位，补齐的空行照样读写一整份状态（fp16 下每个会话约 18 MB），而且所有空行共用一个 scratch 槽。按带宽算，128 个会话时 GDN 已经达到约 89% 的带宽上限。
- **未测到的方向**：400 条序列里有 386 条会被截断，“流式把本不该截的截了”这一方向几乎没测到。

## v7 / v8（T034，2026-09-25/26，结果目录 `results_v7/`、`results_v8/`）：输出与 v6 逐位相同

用户的要求是“不损失精度”。v7 和 v8 只做**输出与 v6 逐位相同**的改动：每一步都保留 PyTorch 的舍入点和运算顺序，
所以阈值、评测结果都原样沿用，不用重新标定。第二张 L20，Round5 权重。

| 版本 | 改动 | 文件 |
|---|---|---|
| v7 | 主机侧：每个档位一块锁页缓冲区，用 numpy 填好后一次异步拷贝（v6 是逐行 Python 循环 + 4 次会阻塞的拷贝）；结果整块拷回（v6 是 clone + 约 154 次拼接）；会话长度放进 numpy 数组。图内：去掉原地 ring 模式下用不到的掩码，读出头的 bf16 权重只转一次，去掉算完就丢的类别头 | [slot_engine_v7.py](slot_engine_v7.py) |
| v8 | 每层的逐元素胶水融合成 Triton kernel：RMSNorm（残差加 + 平方 → `torch.mean` → 收尾）、SiLU×up、短卷积 + SiLU + 卷积状态更新、门控 RMSNorm、q/k norm + 部分 RoPE + 布局；GDN kernel 直接按步长读 q/k/v、自己写 padding 位置的零和平方；ring kernel 直接读 v 和 gate、乘 sigmoid(gate)，单 token 时顺手写回 ring | [slot_engine_v8.py](slot_engine_v8.py)、[fused_kernels.py](fused_kernels.py) |

**怎样保证逐位相同**（[fused_kernels.py](fused_kernels.py) 开头有完整说明）：

- 归约不重写：平方和的均值仍由 `torch.mean` 在同形状、同布局的张量上算，kernel 只负责前后两段；
- exp、rsqrt 用 libdevice，和 PyTorch 里 CUDA 的 `expf`、`rsqrtf` 同源；
- 两处 Triton 默认行为会改变结果，用内联 PTX 固定：
  - Triton 会把“bf16 乘、再 bf16 加”合并成一条 `fma.rn.bf16x2`，只舍入一次（RoPE 里 100 万个值有 25 万个不同）→ 加法用 `add.rn.f32`；
  - Triton 的 `/` 是近似除法，libdevice 又开着 flush-to-zero，而卷积输出里确实有 1e-38 量级的非规格化数 → 除法用 `div.rn.f32`；
- 单测 [test_fused_l20.py](test_fused_l20.py)：每个融合算子对照 v6 的 PyTorch 代码，8 种 (会话, token) 档位，128 项全部逐位相同。

**结果**

| | v6 | v7 | v8 |
|---|---|---|---|
| 与 v6 的差（400 条思考序列 374,953 个位置 / prefix_v2 dev 106,788 个位置） | — | **0 / 0** | **0 / 0** |
| 每个 tick 的 kernel 数（208 个会话，77 行 × 1 token，eager） | 1,647 | 1,647 | **614** |
| 每个 tick 的墙钟时间 / 其中 GPU 图 | 8.49 / 8.11 ms | 8.15 / 8.05 ms | **5.96 / 5.88 ms** |
| P95 ≤ 20 ms 时的会话数 | 208 | 240 | **352** |
| 此时的 token/s | 8,817 | 10,355 | **15,188** |

- 容量按两个种子里较差的一个算，每点 10 秒。v6 一列是 v6 原来的模拟器；换成向量化模拟器（同样的到达模型和随机数）后 v6 是 224，
  差的 16 个会话是模拟器自己每个 tick 用 Python 扫一遍所有会话的开销。
- v8 在 368 个会话时 P95 24 ms，400 以上开始有会话一个 tick 攒到 2 个 token，整个 tick 被补齐到 Lb=2，P95 跳到 54 ms（`sim_high.json`）。
  这是调研报告里的第 5 项（变长打包），只影响边缘负载。
- 顺带测过、没有采用的：cuBLASLt（GPU 时间反而多 0.2 ms，且结果不再逐位相同：概率最大差 0.27，argmax 翻转 325/374,953）；
  矩阵乘法拼接（96 行时整 tick 只省约 0.12 ms，gate+up 拼起来反而更慢）。

**v8 之后的 GPU 时间**（5.88 ms）：GEMM 2.77 ms（291 个 kernel）、GDN 1.63 ms（已到带宽下限）、ring 约 0.9 ms、
其余约 0.6 ms。再往下要改 GEMM 算法或 ring 的分块顺序，结果就不再逐位相同，需要另走精度门槛。
